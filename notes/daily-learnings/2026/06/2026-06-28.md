### ⚠️ 重大事故：C2 commit 漏改

**發生經過：**
- brtclaw 做完 C2 改動後，`git add .openclaw-internal/KB_BACKUP_LOG.md` **單一檔案**，而非 `git add -A`
- 結果 commit `ba76282` 只包含 KB_BACKUP_LOG + 12 個刪除，**漏了 7 個 src/config 改動**
- 後續 C3 期間才發現，要用 `git commit --amend` 修正為 `7f68618`（20 files changed）

**衍生的「一環遞迴」：**
Hubert 23:15 觀察到「一環在一環的往下遞迴」：
- C2 漏 commit → C3 期間發現 → 用 amend 修
- C3 改動又疊加在已修正的 C2 上 → 每次修正都引入新複雜度
- 工作樹狀態變得難以追蹤

**4 個根本問題：**
1. **事實查核不完整** — grep 引用點時沒把「引用路徑常數」與「實際使用」分開
2. **方案描述不精確** — 給 Hubert 看的方案沒列所有副作用
3. **commit 操作不嚴謹** — `git add` 單檔而非 `git add -A`
4. **事後修正又引入新問題** — amend 後又疊加 C3 改動

**MEMORY.md 整合：** 新增「I. 結構性變更 SOP」3 個 SOP（避免 brtclaw 重犯）：
1. **I-1. Commit 前 SOP**：`git add -A` → `git status --short` → `git diff --cached --stat` → commit → `git show HEAD --stat` 驗證
2. **I-2. 事實查核 SOP**：grep 4 個面向（代碼、文件、設定、production prompt）；dead code 與 active 引用分開列
3. **I-3. 方案描述 SOP**：每個方案必含「會連帶改 X、Y、Z」副作用分析
