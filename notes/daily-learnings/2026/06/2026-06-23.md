## What I Learned
- Cron job 失敗有兩種模式：A. Platform FailoverError（status=error，可 retry）/ B. Model stop-short（status=ok 但半成品，failureAlert 抓不到）

- 先量化再決策：headroom vs MiniMax 直連，內建 cache 已有 74% 省，headroom 增量價值小

| 4 | 配送日期精確度不足 | 必須用「YYYY-MM-DD 週X」格式，不可說「下週」 |

**A2 架構決策（為何放棄 quick reply）：**

**舊版失敗原因：**
- LLM 把 quick reply 結構當作文字輸出（不是 LINE 訊息物件）
- OpenClaw 把 LLM 輸出視為純文字，自動包成 LINE 文字訊息
- 「架構錯位」：**LINE 訊息結構不該由 LLM 決定**

**A2 架構：**
- LLM 不介入訂單建立流程
- 訂單流程由 **LINE Rich Menu + Worker 狀態機**驅動
- LLM 只負責：FAQ、菜單查詢、訂單查詢、修改訂單、催付款
- LLM **不**輸出：quick reply、Flex Message、任何 LINE API 結構

**流程：**
```
客戶點 Rich Menu「我要訂購」
  → LINE 原生觸發
  → Worker 狀態機引導依序輸入
  → 客戶輸入「確認」/「送出」
  → Worker 呼叫 API → 寫入 CSV（< 100ms）
  → Worker push 通知 Hubert
```

### Headroom 效益量化 + 最終決策切回 direct MiniMax

**調研結果：**
- Production LLM gateway 該監控 4 大指標：Latency / Cache hit / Error rate / Token usage
- Headroom 內建 `/metrics` Prometheus 端點有：requests / cached / failed / tokens / latency / overhead / ttfb
- 缺：p50/p95/p99、Cache hit rate %、Anthropic prompt cache 觸發率、Baseline 對照組

**真實效益計算（觀察期 30 個 request / 2.5M tokens）：**

| 模式 | 算法 | 成本 |
|------|------|------|
| Direct MiniMax（baseline）| 2.5M × $0.6/1M input | $1.50 |
| With headroom cache 模式 | 28/30 觸發 cacheRead | $0.384 |
| 表面省 | $1.12（74%）| — |

**關鍵洞察：** 74% 不是 headroom 的功勞，是 **MiniMax 內建的 Anthropic prompt caching**。OpenClaw SDK 自己會送 `cache_control` header，所以**直接打 MiniMax 也會有 74% cacheRead 命中率**。

**headroom 對便宜 provider 的價值：**
| Provider | Input | CacheRead | headroom 省 50% 美元價值 |
|----------|-------|-----------|--------------------------|
| Claude Sonnet | $3/1M | $0.3/1M | 巨大 |
| MiniMax-M3 | $0.6/1M | $0.12/1M | 小（5x 成本差）|

**最終決策（Hubert 同意）：切回 raw typing input（direct MiniMax）**

6 步驟：
1. `endpoint-switch.sh direct`（會 restart OpenClaw，session 中斷）
2. 新 session 驗證 baseUrl = `https://api.minimax.io/anthropic`
3. headroom proxy 保留運行
4. monitor cron **不設**
5. headroom PLAN v2.1 + scripts v2.2 全部保留
6. 不刪除任何檔案

### Headroom 規劃：先 PLAN 後實作

**教訓：** brtclaw 太急著實作 Step 1，沒讀完整操作手冊。Hubert 修正：
- 先 Planning、後實作
- 完成 `headroom/PLAN.md`（17 KB / 410 行）
- 完成 `i-en-video-test/PLANNING.md`（12 KB / 351 行）
- 不動手實作，全部留給新 session

**Headroom proxy CLI 模式（正確理解）：**
- `--mode token`（重寫 turns，最大節省，**會破壞 KV cache**）
- `--mode cache`（凍結 turns，最大 cache 命中，**保守**）
- `--no-optimize`（完全 passthrough）

**為什麼 `token` 模式對 brtclaw 風險特別高：**
- M3 設定 `cacheRead: 0.12`（比 input 0.6 便宜 **5x**）
- Anthropic prompt cache：prefix 穩定 → cache 命中 → 省 80% input 成本
- headroom `token` 模式會**重寫之前的 turns** → 破壞 prefix → cache 命中率歸零
- 結果可能「token 數省了 30% 但 cache miss 增加 → 總成本反而變高」

**新推薦：**
- Step 4a（首週）→ `--mode cache`（保守，cache 命中率高）
- Step 4b（第二週）→ 視數據決定要不要切 token
- 永遠保留 `--no-optimize`（緊急 fallback）

### 今日 lesson learned（11 條）

1. Cron job 的「summary」欄位 = 模型最終輸出，模型陷入規劃模式時半成品會被當成 summary 送出
2. Output token 是有限資源，模型必須學會「用 tool call 而非文字」來做 planning
3. 失敗時也要寫檔（.md 檔是資料正確性的最低保障）
4. failureAlert 抓不到「model ok 但報告空」的「假成功」狀態
5. 兩種失敗模式要分開處理（平台錯誤靠 retry，模型錯誤靠 prompt + 預檢）
6. 「架構錯位」是 LLM 應用常見盲點，LINE 結構化訊息不該由 LLM 直接生成
7. push vs reply 是 LINE 客服核心分層，必須在 prompt 明確對照
8. 「不確定就轉真人」要有完整 SOP（push 通知 + 等待回覆流程）
9. 客戶體驗細節常被忽略（不會出現在 LLM benchmark，但對客戶是決定體驗的關鍵）
10. 空泛指令是 brtclaw 的陷阱（必須有可操作 SOP）
11. 先量化成本再決定整合（MiniMax 內建 cache 74% 省，headroom 增量價值小）
