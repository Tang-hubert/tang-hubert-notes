### Cognee Memory 調查與修復

**發現的問題：**

| 問題 | 描述 |
|------|------|
| A | Session 停滯（stalled）→ 隔天失去進度（根因：before_prompt_build hook timeout）|
| B | 跨 session 資訊召回（autoRecall）— 對客服可能是雙面刃 |
| C | Cognee Server `LLMProvider` enum 缺少 `minimax` |

**已套用修復：**
- ✅ `cognee-openclaw` config 加入 `requestTimeoutMs: 5000`（5秒 timeout）
- ✅ Gateway 重啟成功，config 驗證通過
- ✅ 確認 Cognee recall 正常運作（登入→recall 來回約 1-4 秒）

**P1 待處理：**
- 確認 cognee-openclaw plugin 呼叫 `/api/v1/recall` 時 auth token 是否正確傳遞（懷疑 JWT 可能未在首次請求前取得）

### 問答澄清（Hubert 提問）

**Q1: Session 隔天就失去進度？需要修正嗎？**
- 答：已修正（加入 timeout）。長期可考慮降到 3000ms 或 `autoRecall: false`

**Q2: 不同 session 資訊連動？需要修正嗎？**
- 答：架構上已符合期待
  - 不同 LINE user ID → 不同 session（`dmScope: per-channel-peer`）
  - 同一 user session 保持，不會因時間自動刷新
  - 刷新只發生在：stalled recovery、`/reset`、嚴重 context overflow

**Q3: `memoryFlush` 的意義？**
- 答：compaction 前自動執行看不見的 agent turn，寫入 memory 檔案
- ✅ 好處：不需手動提醒
- ⚠️ 限制：只在 compaction 觸發，需設定專用 model（建議 `ollama/qwen3:8b`）
- 💡 建議：客服這類固定腳本用應用，手動提醒更精準；main agent 開啟較有價值
