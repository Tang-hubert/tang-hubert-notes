### External-User LINE Bot: Payment Info Defense

**Problem:** LLM-generated bank account info risks hallucination. LINE Auto Reply only triggers on exact text match, not partial/keyword — useless for varied "how to pay" queries.

**Solution — Three-Layer Architecture:**

| Layer | Location | Mechanism |
|-------|----------|-----------|
| Layer 1 | Cloudflare Worker | Payment keyword detection (帳號/匯款/轉帳/付款/銀行...) → intercept & reply static text → skip OpenClaw |
| Layer 2 | Agent Prompt | Static template `bank_account_template()` function returns fixed text from file |
| Layer 3 | Human | Hubert manages `static/payment_info.txt` directly, no AI generation |

**Why Worker is best for Layer 1:**
```
LINE Message → Worker checks keywords
                     ├── Match (帳號/匯款/...) → reply static text → DONE
                     └── No match → forward to OpenClaw
```

**Bonus: Per-user rate limiting (7/min)** — confirmed Worker uses `userId` as KV key, fully isolated per user.

### Cloudflare KV Dynamic Payment Info

**Design:** Payment info stored in KV (`payment_info` key), Worker reads with 60s cache.

**Benefits:**
- Update bank account without redeploying Worker (single `wrangler kv:key put` command)
- Future-ready for admin UI / productization
- Hubert manages `static/payment_info.txt` as source of truth

**File structure:**
```
external-user/
├── static/
│   └── payment_info.txt       # Payment info (Hubert-managed)
├── data/
│   └── transfer_records.csv   # CSV reserved for transfer records
└── cloudflare-worker/         # Worker code
```

### Per-user Rate Limiting Confirmed

**Question:** Rate Limiting is per-user or global?

**Answer:** Per-user, fully isolated.

Worker uses `userId` as KV key:
```typescript
const windowKey = `rl:${userId}:window`;  // ← per userId
const dailyKey = `rl:${userId}:daily`;
```

User A sending 30 messages doesn't affect User B.

**Tuning:** Adjusted to **7/min** (down from 30/min) for stricter customer service use case.

### Concurrent Message Handling

**Question:** 3+ users sending at once — queue or busy signal?

**Answer:** No queue. Asynchronous processing.

```
LINE → Worker (validates + acknowledges immediately) → OpenClaw processes async
```

- LINE shows "loading..." animation while LLM responds
- cron "busy" state is separate (TaskFlow `in_progress`) — not related to real-time messaging
