#### Phase B — Check 1 npm test 修法

**初判誤導**：看到「CSV 行數 122 = 61 × 2」直覺是 csvWriter.js 的 proper-lockfile 鎖失效 → production race condition 真實風險

**正確 root cause（修正後）**：
- 「concurrency test」實際用 `spawnSync` 是 **sequential** 不是 concurrent，所以 race condition 物理上不可能發生在同一個 test run 內
- 122 行 = 前次 run 失敗留下 `_csv_concurrency_test/2099-12-31.csv` + `_csv_concurrency_test.lock/` sibling dir
- 下次 run setup 只清資料目錄不清 lock dir → lock dir 殘留導致 busy-wait 5s → stale lock 解開後第二次 writeOrder 看到「file 為空」(因為 fs.rmSync 已清) → isNewFile=true → 重寫 header → 然後第一次 run 殘留的 60 筆又被 append 一次（但實際上 lock 失效可能讓 first batch 寫了兩次）

**修法**：`tests/csv-writer-concurrency.test.js`
- Setup 加 `LOCK_DIR_SIBLING = data/orders/_csv_concurrency_test.lock` 預先清除 stale state
- Cleanup 加同樣 LOCK_DIR_SIBLING 清除

**驗證**：
- 單獨跑（clean）→ PASS 61 行
- 注入 stale state 跑 → PASS（cleanup 起作用）
- 3 次連跑 → 全 PASS
- 全套 npm test → PASS
- check-quality → 12/0/0（commit 後）
